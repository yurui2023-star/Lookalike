1. Overview and customer changes

This document is the implementation-level design for SAD V1.0 (SAD REF-05). Customer confirmation: no Lookalike frontend; after models are built and published in pre-production, monthly batch scoring of the full eligible candidate set; scores synced to Sales CDP using the attached field schema. File upload and Segment-based scoring are retired.

1.1 Meaning of “full-population scoring”

“Score all customers monthly” means: score every valid customer in the frozen monthly candidate snapshot that Smart Sales built from product eligibility, active-status, exclusion-list, and compliance rules. Inference applies no threshold and no Top-K. Filtering and list building stay in Smart Sales after it reads CDP. This is not scoring the bank-wide customer master (SAD reference ~35.72M).

5. Monthly batch flow

sequenceDiagram participant SS as Smart Sales participant SCH as Scheduler participant LA as Lookalike participant REG as Registry participant DP as Handover participant CDP as ClickHouse SS->>DP: Publish candidate snapshot SCH->>LA: POST /runs LA->>LA: Validate idempotency, snapshots, published model LA->>REG: Load artifact + checksum + schema LA->>DP: Read candidate ∩ features by shard LA->>LA: Full inference without threshold LA->>CDP: Idempotent write staging LA->>CDP: Reconcile then publish LA->>SCH: SUCCEEDED SS->>CDP: Read published batch only

States: PENDING → VALIDATING → RUNNING → SUCCEEDED / FAILED; transient errors → RETRYING (max 3); cancel → CANCELLED. ClickHouse writes stay staging until count reconciliation sets published. Duplicate idempotency keys must not create uncontrolled extra runs. A controlled rerun uses a new run_batch_id linked to the original and must not overwrite published history.

7. Inference runtime

  1. Resolve the approved published artifact (model, preprocessor, ordered feature_list, impute/P99, schema version); verify checksum/signature.
  2. Freeze candidate snapshot, feature snapshot, and model version for the run.
  3. JOIN candidates to features; record valid/invalid; apply published missing-value rules.
  4. Hard-fail on leakage denylist hits.
  5. Score shards of 50,000 rows; predict_proba is the Lookalike score, clipped to [0, 1].
  6. Every valid candidate receives a score; no score filter.
  7. Commit shards idempotently; update checkpoints.
  8. Publish only after candidate / valid / scored / written counts reconcile.

Production does not train, recompute IV, reselect features, apply a similarity threshold, build Segments, or exclude “seed” IDs from the candidate snapshot. Cold-start rows classified as invalid by the published spec are counted with a reason code, not dropped silently.

Lite capacity runs the two products serially by default. Parallel execution requires a quota recalculation. Workers are routed by productCode.

The spreadsheet title says “Model ID x Profile ID”; the description says “process ID joined with Profile ID”. This design follows the description: the left side is run_batch_id. Using model_id alone would collide across months and violate SAD isolation and non-overwrite of published history.

Technical columns on the same table (do not replace the six business fields): run_batch_id, scoring_month, model_version, snapshot IDs, scored_at, trace_id, publish_status, rerun_of. Logical uniqueness: product_id + run_batch_id + profile_id + model_version. Results must not include national IDs, full account numbers, or the raw feature vector.

  1. Batch INSERT (suggested 5,000); idempotent on lookalike_key.
  2. Write as staging; Smart Sales may read only published.
  3. After reconciliation, mark published.
  4. On reconciliation failure keep staging and fail the run (5102).
  5. Lookalike does not implement a second REST/SFTP/Kafka business sync path.

10. Artifact loading and pre-production boundary

Production Lookalike does not build samples, select features, train, or tune. It only loads approved published artifacts.

Pre-production (outside the production path): bank-defined seeds and T0; governed train/validate/OOT; EDA, IV, missing/identical filters, P99; LightGBM primary and optional LR+WOE; governance approval of version, schema, checksum, effective time, rollback.

Quality gates (subject to model governance): drop missing >95% or identical >95% or IV <0.02; approved P99 for skew; no post-T0 outcome/approval/disbursement/marketing-feedback fields. Filters and imputes freeze into the artifact; production executes them and does not reselect features.

Load failure (unpublished, product mismatch, schema mismatch, checksum) fails the run. Do not silently substitute a cached older version unless the request names a still-published rollback version.

Monthly PSI uses 0.25 as the current reference baseline. Breach raises an alert ticket; production does not auto-train or auto-cut traffic. The next monthly run picks up a newly published version after governance.

11. Feature alignment and leakage control

Reuse src/lookalike/adapters/ and leakage.py (ResponsePropensity, post-disbursement fields, ID numbers, CIF). Eligibility-constant columns must not enter the feature matrix. DESIGN_PLAN finding F-03 still applies in pre-production: label-defining columns in the feature set produce AUC≈1.0 and rank existing holders first. Map logical customer_id to CDP profile_id; HostCif / personal_cif mapping is SAD P-03.

12. Security and audit

  • No business users or page sessions; separate least-privilege system identities.
  • Secrets stay out of code, images, and requirement files.
  • Logs must not contain national IDs, full account numbers, credentials, model secrets, or unnecessary feature values.
  • Audit: trigger, validation, model load, I/O, state change, retry, failure — with run_batch_id, trace_id, identity, result, error code.

14. Test design

Unit: composite key, idempotency, denylist hard-fail, train/serve preprocessor parity, state machine. Contract: scheduler required fields; six CDP business fields plus lineage columns; unpublished batches not consumable. Integration: JOIN, checkpoint resume, failed reconciliation, rerun new batch. Performance gates: 3.0M and 6.0M. Negative cases: unpublished model, schema drift, denylist residue, duplicate submit, candidate not ready, partial ClickHouse write, constructing the key from model_id instead of run_batch_id.

Keep tests/test_adapters.py and tests/test_lookalike.py as pre-production regression. Add tests/test_cdp_schema.py and tests/test_run_orchestrator.py. Drop upload/Segment acceptance tests.

ADRs

  1. Production form is a headless batch inference service, not an interactive Lookalike platform.
  2. Scoring population is the Smart Sales candidate snapshot, not the bank-wide master and not user upload/Segment.
  3. CDP path is idempotent ClickHouse write + publish after reconciliation; the six spreadsheet fields are the business contract.
  4. Composite-key left side is run_batch_id (process ID), not model_id alone.
  5. Train/serve split; no training stack in the production image; PSI does not auto-cutover.
  6. Lookalike does not call CRM; thresholds and selection stay in Smart Sales.
  7. Scores are for marketing ranking only, not credit decisions.
