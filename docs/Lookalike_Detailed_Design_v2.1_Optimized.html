0. 优化总览 OPTIMIZED

结论：v2.0 业务对齐度高（双产品、71+24 特征、LR+LightGBM、阈值后置、全量打分），但存在一期过重、与现有仓库脱节、若干技术矛盾、落地顺序不清。v2.1 在不削弱 BRD 目标的前提下，把方案改成「可在当前 FastAPI 仓库上分阶段演进」的工程设计。

0.1 v2.0 保留的正确设计

  • Score / Threshold 分离；Generate 对 100% 有效候选打分
  • 双产品（Personal Unsecured Loan / Mortgage）独立种子与模型
  • LightGBM 主模型 + LR+WOE 可解释基线
  • 缺失率 / 同值率 / IV / P99 质量筛选；时间泄漏审计强制执行
  • Version 不可变；Dashboard 直方图预计算；导出 >10,000 行拆分
  • PSI 监控与公平性评估方向正确

0.2 v2.0 → v2.1 关键优化点

2.1 关键修正：训练 ≠ 打分

Offline（训练）
  • 按产品定义 Seed / Negative
  • Observation / Performance Window
  • WOE/IV、泄漏审计、OOT
  • 产出：模型文件、feature_list、woe_maps、metrics
  • 频率：月度 / PSI 触发，不跟每次 Generate 绑定
Online（打分）
  • 加载已部署模型版本
  • 对候选集批量推理
  • 写 version + scores + histogram
  • 阈值仅在 Dashboard / Export 使用
  • 频率：用户触发或 Recurring

5. 特征工程与防泄漏（落地规则）

保留 v2.0 流水线顺序，补充可执行判定：

flowchart LR A[Extract] --> B[Same-CIF Exclude] B --> C[Cold-start Filter] C --> D[Missing / Identical / IV Screen] D --> E[P99 Cap if skew high] E --> F[Temporal Leakage Audit] F --> G[WOE for LR / Raw for LGB] G --> H[Feature Store / Artifact]

5.1 Cold Start 过滤（补齐）

规则定义动作
无有效行为Observation Window 内交易次数=0 且 App 活跃天数为 0不进入 Lookalike 覆盖；计入 insufficient_data
身份无法映射上传 ID 无法匹配 CDP HostCif / 备用键计入 unmapped；不打分
硬性不合格不满足产品 eligibility不进候选池（与负样本定义区分）

5.2 时间泄漏强制清单（训练前阻断）

  • 放款后才存在的字段（当前贷款余额、放款日）
  • 营销触达结果（接触后才知道）
  • 他模型输出分（如 ResponsePropensity）
  • 纯标识字段（CIF、证件号）
  • 候选池内恒定的 eligibility 字段（无区分度）
任一 denylist 字段残留 → 训练任务失败并写 Audit，不允许「警告后继续」。

5.3 Event Importance / RFM（BRD 补齐）

对 Observation Window 内每个业务 Event（Deposit / Transfer / Billing / App Login…）计算：

  • Recency：距最近一次事件天数
  • Frequency：窗口内次数
  • Monetary：窗口内金额均值或总和（按事件定义）

Dashboard 同时展示：静态 Feature Importance（模型 gain/WOE）与 Event Importance（RFM 相关或置换重要性）。MVP 可先用模型特征重要性近似，P1 补 RFM 报表。

6. 双产品双轨建模（修正一致性）

统一口径：每产品训练 LR+WOE（baseline） 与 LightGBM（primary）。推理默认 primary；监管/解释场景可切换 baseline。

6.1 样本定义（保留 v2.0，强调负样本语义）

  • 正样本：已获批并放款、逾期可控、满足观察期
  • 负样本：有机会但未转化的合格客群，不是「坏客户」
  • 排除：员工/测试/销户/身故/硬性不合格

6.2 切分与评估

项v2.1 规定
随机切分60/20/20，分层抽样
OOT必须；时间窗晚于训练窗
技术指标AUC、KS、AP、Lift@Top20% — 诊断用，不设一刀切门槛
业务验收A/B 或 holdout 投放：高分段转化 ≥ 对照组；Top20% Lift ≥ 1.2 作为参考目标而非硬门禁
过拟合报告 Train-Test KS 差；异常则阻断部署

6.3 Model Registry 最小字段

model_registry:

7.2 scoring_result 优化 COST

-- v2.0 风险：每行塞 feature_values JSONB → 百万级膨胀
-- v2.1 默认：
CREATE TABLE scoring_result (
  version_id   BIGINT NOT NULL,
  customer_key TEXT   NOT NULL,
  similarity_score NUMERIC(6,4) NOT NULL,
  score_rank   INT,
  scored_at    TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (version_id, customer_key)
) PARTITION BY LIST (version_id);

-- 可选明细表（抽样或按需物化，不做默认写入）
-- scoring_feature_detail(version_id, customer_key, features JSONB)

7.3 保留策略

  • Completed version 原始分：默认保留 90 天，可配置
  • analysis_snapshot 与 export_history：保留更久（≥12 个月）供 Recurring 对比
  • audit_log：不可 UPDATE/DELETE（保留 v2.0 触发器）

8.2 API 演进原则

  • MVP 保持现有 5 个核心端点，不一次上 30+ 接口
  • P1 引入 process/version 资源后，旧端点标记 deprecated，保留 1 个大版本兼容
  • 阈值参数只出现在 Dashboard / Export / Classify，不出现在 Create Process
  • Generate 始终异步（P1）；返回 version_id + WebSocket/轮询进度

9. 打分与 Dashboard 性能优化

场景v2.0v2.1 优化
批量推理10k batch保留；按模型内存自适应 5k–50k；失败批次可重试
阈值滑条Redis 100-bin 直方图本地求和保留；首屏只拉 snapshot，不扫明细表

10. 前端范围裁剪

  • MVP：不强制前端；Swagger + CLI 即可验证模型与打分
  • P1：可先做最小 Process 控制台（列表 / 创建 / 进度 / Dashboard），或继续 API-only
  • P2：落地 v2.0 的 8 个 BRD 参考屏（Ant Design Pro）
避免「前端 8 屏与后端契约未稳时并行大开」——先冻结 Dashboard / Generate / Export 的 JSON 契约再铺 UI。

11. 安全 / 公平性 / 监控

安全（优化）
  • P1：企业 SSO / OIDC，不用长期自建用户库
  • RBAC：Marketing / DS / Admin / Auditor
  • 导出下载短时签名 URL
  • 审计日志不可篡改
公平性与监控
  • 按 gender / age_band / region 监控转化率差
  • PSI > 0.25 → 告警工单，不自动盲切流量
  • 重训需人工 Approve 后切换 primary
  • 敏感特征默认不进入解释文案对外展示

12.1 决策记录（ADR 摘要）

  1. 推理主模型固定为 LightGBM；LR 仅解释/合规。
  2. 阈值永不进入 Create Process 输入。
  3. 训练与 Generate 解耦；Generate 只读已部署模型。
  4. scoring_result 不默认存全量特征快照。
  5. 前端完整 8 屏放到 P2，不阻塞模型价值验证。
落地建议（下一步）： 1）按本文件把仓库目录演进到 api/ + adapters/； 2）为真实 CSV 固化 Feature Adapter 与泄漏 denylist 单测； 3）P1 引入 process_version + 异步打分，再考虑 React。
