1. Design Overview & Principles

This document is the Lookalike Detailed Design v2.1 (complete). BRD capabilities are preserved, delivered in MVP → P1 → P2 phases, and aligned with the existing FastAPI + LightGBM repository. Full frontend and external integrations are P2.

1.1 Product Goal

Lookalike Audience & Lead Generation is an AI audience-expansion capability inside Smart Sale CDP. Given a product Project Model seed (Sample), it scores Potential candidates with a Similarity Score (0–1), produces Lookalike sets, feature importance, and dashboards, supports export/Segment, and can track conversion.

1.2 Design Principles

  1. Score–threshold separation: Create Process does not collect Similarity Threshold; Generate scores 100% of valid candidates; threshold is for Dashboard/Export only.
  2. Version immutability: each run creates an independent Version with a frozen config snapshot.
  3. Train/serve split: offline training writes Model Registry; online Generate loads deployed models only.
  4. Zero tolerance for temporal leakage: mandatory denylist audit before training; hard fail on hit.
  5. Dual-model independence: per product LightGBM (primary) + LR+WOE (explainable baseline).
  6. Cold-start exclusion: customers with no transaction/App activity are not covered.
  7. No fixed metric gates: AUC/KS are diagnostic; business success is Lift/A/B.

5.1 Quality Rules

SkewnessHighP99 capping
Imputation—Median / mode

5.2 Temporal Leakage Denylist (Hard Fail)

  • Post-disbursement fields (current loan balance, disbursement date)
  • Post-contact outcomes; other-model scores (e.g. ResponsePropensity)
  • Pure identifiers (CIF, ID number)
  • Constant eligibility fields inside the candidate pool
Any denylist residual → fail training/prep and write audit. No “warn and continue”.

5.3 Cold Start

Zero transactions and zero App active days in the Observation Window → insufficient_data, not scored. Unmapped identity → unmapped.

5.4 Event Importance / RFM

Compute Recency / Frequency / Monetary per Event in the Observation Window. Dashboard shows static Feature Importance and Event Importance. MVP may approximate with model gain; P1 adds RFM reporting.

6. Model Training (Dual-Product Dual-Track)

Per product: train LightGBM (primary) and LR+WOE (baseline). Inference defaults to primary. XGBoost is backup only — not in phase-1 scope.
flowchart TB subgraph PUL[Personal Unsecured Loan] S1[Positives 12M]-->N1[Negatives: eligible non-converters] N1-->D1[60/20/20 + OOT] D1-->L1[LR+WOE] D1-->G1[LightGBM] L1-->R1[Registry] G1-->R1 end subgraph ML[Mortgage / Business Loan] S2[Positives 24M]-->N2[Negatives] N2-->D2[60/20/20 + OOT] D2-->L2[LR+WOE] D2-->G2[LightGBM] L2-->R2[Registry] G2-->R2 end

6.1 Sample Semantics

  • Positives: approved + disbursed, controlled delinquency, observation tenure met
  • Negatives: eligible customers who had opportunity but did not convert — not “bad customers”
  • Exclusions: employees, test accounts, closed/deceased, hard ineligibility

11. Inference & Scoring Pipeline

  1. Load deployed primary model + feature_list
  2. Identity mapping; filter unmapped / cold-start / hard-ineligible
  3. Adapter → clean → batch predict_proba as Similarity Score
  4. Write scoring_result (key+score+rank) and analysis_snapshot (histogram…)
  5. Dashboard/Export filter by threshold without re-scoring
count(score >= t) = sum(histogram.counts[i] for bin_i >= t)

13. Security, Compliance & Fairness

  • P1: enterprise SSO/OIDC; RBAC (Marketing / DS / Admin / Auditor)
  • Short-lived signed export URLs; immutable audit log
  • Fairness monitoring by gender / age_band / region response differentials
  • Sensitive features excluded from external explanation copy by default
  • Third-party data under contract and minimization principles

14. Model Monitoring & Retraining

  • Monthly PSI; feature/score PSI > 0.25 → alert ticket, no blind traffic cutover
  • Retrain requires human Approve; canary 30% → 50% → 100% with rollback
  • Registry states: training → validated → deployed → retired

18.1 ADR Summary

  1. Primary inference model = LightGBM; LR for explainability/compliance only.
  2. Threshold never enters Create Process.
  3. Training and Generate are decoupled.
  4. scoring_result stores key+score by default.
  5. Full frontend is P2.
